2.8  CONTACT FORM — CONVERTED TO NETLIFY FORMS
-------------------------------------------------------------------------------
Objective: form submissions delivered to somesh@sreshtaenviro.com without
standing up a backend, database or API. Netlify Forms chosen because the site
already deploys there; approach specified by the client and implemented as
briefed, with several defects found and corrected along the way.

  ARCHITECTURE
    Visitor -> HTML form -> Netlify Forms -> stores submission
                                          -> email notification -> inbox
    No database, no CMS, no serverless function, no third-party form service.

  DEFECTS FOUND IN THE EXISTING FORM
    a) method="get"
       A GET form serialises fields into the URL and never sends a request
       body. Netlify would have received nothing. Changed to POST.

    b) Dropdown values were untouched Webflow placeholders
         <option value="Webflow Design">Waste water Treatment</option>
         <option value="Webflow Development">underground water</option>
         <option value="Webflow E-commerce">residential water</option>
       The visible label and the submitted value disagreed completely. Every
       notification email would have read "Subject: Webflow Design" regardless
       of what the visitor picked. Values rewritten to match labels.

    c) Duplicate "Subject" label
       Both the <select> and the <textarea> were labelled "Subject".
       Textarea relabelled "Message"; placeholder changed from
       "Enter your message..." to "Tell us about your project...".

    d) Field names unfit for email output
       name="Number" -> name="phone"
       name="field"  -> name="subject"
       name="Message"-> name="message"
       Netlify prints raw field names in the notification, so these would have
       arrived as "Number:" and "Field:".

    e) No empty-value guard on the select
       First option was value="Enter your subject..." — a placeholder that
       would submit as real data. Changed to value="" plus required, so the
       browser blocks submission until a real choice is made.

  NETLIFY WIRING ADDED
    <form name="contact" method="POST" data-netlify="true"
          data-netlify-honeypot="bot-field">
    <input type="hidden" name="form-name" value="contact">   <- routes the
                                                                submission
    Honeypot field wrapped in .hidden-field, hidden via clip-rect rather than
    display:none (some bots skip display:none fields, defeating the trap).

  THE NON-OBVIOUS PROBLEM — WEBFLOW INTERCEPTS THE SUBMIT
    contact.html still loads js/hydromax.js, the exported Webflow runtime.
    It binds a jQuery submit handler to any form inside a .w-form wrapper and
    POSTs to Webflow's own endpoint. The wrapper div here carries class
    "form-main w-form", so Webflow's handler applies.

    Left unaddressed this fails silently and expensively: the form appears to
    submit, Webflow's success state may even render, and Netlify never
    receives a single submission. Nothing in the UI would reveal the loss.

    SOLUTION — js/contact-form.js (new file)
      Registers its submit listener on the CAPTURE phase (addEventListener
      third argument = true). Capture runs top-down before bubbling, so this
      handler executes before Webflow's. It then calls:
        e.preventDefault()
        e.stopPropagation()
        e.stopImmediatePropagation()
      which prevents Webflow's handler from ever running.

      It then performs the AJAX submission itself:
        - runs native checkValidity() / reportValidity() first
        - disables the button, sets label to "Sending..."
        - builds a urlencoded body from FormData (form-name included)
        - fetch('/', POST, Content-Type application/x-www-form-urlencoded)
        - on success: hides the form, reveals the inline success panel,
          smooth-scrolls it into view
        - on failure: reveals the error panel, re-enables the button and
          restores its label
      Result: no redirect to Netlify's default confirmation page; the
      designed form UI is preserved.

  COPY CHANGES
    Heading: "Let's Build Energy Together"
          -> "Let's Talk About Your Water Project"
    (the original was inherited from the renewable-energy template and did not
    describe this business)
    Error panel now names a fallback address: somesh@sreshtaenviro.com

  SUBJECT OPTIONS (final)

3.1  HERO VIDEO
-------------------------------------------------------------------------------
  MEASURED (ffprobe):
    videos/hydro.mp4
      size       16,376,856 bytes  (16.4 MB)
      duration   11.934 s
      resolution 1920x1080, 30fps, h264
      bitrate    10,978,284 bps  (~11.0 Mbps)
      audio      none

  DIAGNOSIS
    ~11 Mbps is near Blu-ray density for a muted decorative background loop.
    The browser cannot buffer faster than playback consumes, so it stalls,
    paints a single frame, and stalls again — exactly the reported symptom.

    Also checked the MP4 atom order, since a trailing moov atom forces a full
    download before first paint and produces identical symptoms:
      ftyp(32) -> free(8) -> moov(2,541) -> uuid(3,492) -> mdat(16,370,783)
    moov precedes mdat, so faststart was already correct. Ruled out.
    Bitrate was the sole cause.

  FIX — re-encoded the same footage, nothing swapped out:
    -an                       strip audio (element is muted anyway)
    -c:v libx264 -crf 30 -preset slow
    -g 60 -keyint_min 60 -sc_threshold 0   keyframe every 2s
    -movflags +faststart      moov ahead of mdat, verified after encode
    -pix_fmt yuv420p          Safari/iOS compatibility

                     BEFORE          AFTER
    size             16.4 MB         3.1 MB      (5.2x smaller)
    bitrate          11.0 Mbps       2.1 Mbps
    resolution       1920x1080       1920x1080   (unchanged)
    duration         11.934 s        11.934 s    (unchanged)

    Output written as videos/hydro-web.mp4. Original hydro.mp4 left in place,
    so the change is reversible.

    Poster added: videos/hydro-poster.jpg (124 KB), extracted from frame 0 of
    the video itself — so the still-to-motion transition is seamless. Applied
    as both the poster attribute and a CSS background-image, giving an instant
    paint with no blank gap. Wired into index.html and pumps.html.

  ON CLOUDINARY (client asked whether a CDN would fix it)
    Assessed and advised against for now. Netlify already serves from a CDN,
    so distribution was not the bottleneck — the file being 5x larger than
    necessary was. Cloudinary's real value is automatic format negotiation
    (AV1/WebM per browser) and on-the-fly resizing; worth revisiting if video
    volume grows, but unnecessary at 3.1 MB.

  WEBM CONSIDERED AND REJECTED

    Discarded, to avoid browsers selecting the heavier file.

3.2  PORTFOLIO SECTION — "Pumping Systems Designed To Meet Your Needs"
-------------------------------------------------------------------------------
  The heaviest section on the site: 80 MB across four tiles, all committed
  21 May and untouched since.

  ROOT CAUSE
    Three tiles were animated GIFs at 1152x648. GIF has no interframe
    compression — every frame stores as a near-complete image, which is why
    121-210 frames cost 18-35 MB. The fourth was a 5500x3669 JPEG displayed
    in an 862px slot: roughly 4x more pixels than can ever be shown.

  RESULTS
    asset      before              after            reduction
    p111       35 MB GIF (121f)    338 KB MP4       106x
    p13        20 MB GIF (210f)    552 KB MP4        36x
    p12        18 MB GIF (152f)    550 KB MP4        33x
    ss1.jpg    8.8 MB (5500px)     218 KB (1724px)   41x
    ---------------------------------------------------------
    TOTAL      80 MB               1.9 MB           ~42x

  IMPLEMENTATION
    GIFs became <video autoplay loop muted playsinline preload="metadata">
    with a poster from each clip's own first frame. Visual behaviour is
    identical — silent looping motion.

    Required CSS addition (hydromax.style.css):
      video.portfolio-img { display:block; width:100%; height:auto;
                            max-width:100%; object-fit:cover; }
    Necessary because <video> does not inherit the browser's <img> layout
    defaults — without it the tiles collapse to the 300px default video width.
    Class names and the reveal-wrap / reveal-frame animation markup untouched.

    ss1.jpg resized to 1724px wide (2x the 862px display slot) as ss1-web.jpg.

PART 4 — PROBLEMS ENCOUNTERED AND HOW THEY WERE RESOLVED
===============================================================================

ISSUE 1 — sed delimiter collision
  Symptom : "unknown option to `s'" x7 when rewriting page titles.
  Cause   : replacement text "About | Hydromax" contained the pipe character
            being used as the sed s||| delimiter.
  Fix     : rewrote as Python literal string replacement. Verified all 7.

ISSUE 2 — invisible non-breaking space
  Symptom : footer replacement matched 4 of 12 files; 8 reported MISMATCH
            despite the text appearing identical.
  Cause   : \xa0 (non-breaking space) rather than a normal space between
            "Developed by" and the <a> tag.
  Fix     : inspected raw bytes with Python repr(), matched \xa0 explicitly.

ISSUE 3 — 7-step workflow would not animate  (ultimately reverted)
  Symptom : left timeline dots only filled to 04; steps 05-07 stayed grey and
            fell out of sync with the right-hand cards while scrolling.
  Cause   : Webflow's "a-21" step-sticky-animation is a compiled scroll-progress
            scrubber with keyframes hardcoded for exactly four steps
            (.step-card._1st/._2nd/._3rd/._4rd at keyframes 42/45/50/54/57/60).
            Steps 5-7 had no keyframes, so nothing ever targeted them.
  Attempt 1: js/step-sync.js using scroll listener + CSS classes with
            !important. Failed — Webflow writes inline styles every frame,
            which outrank stylesheet rules.
  Attempt 2: permanent requestAnimationFrame loop overwriting the inline
            styles directly each frame. Also did not hold.
  Resolution: client elected to return to 4 steps and nest the extra phases
            as sub-points inside steps 03 and 04. This works with Webflow's
            native animation rather than against it — the better outcome, and
            the reason the current section behaves correctly.
            step-sync.js removed from about.html.

ISSUE 4 — Webflow runtime would have silently eaten form submissions
  Symptom : anticipated, not observed — caught by inspection before deploy.
  Cause   : hydromax.js (Webflow export runtime) binds a submit handler to any
            form inside .w-form and POSTs to Webflow's endpoint. The contact
            form's wrapper is class="form-main w-form", so it qualified.
            Netlify would have received zero submissions while the UI showed
            apparent success — a silent, invisible failure mode.
  Fix     : js/contact-form.js listens on the capture phase and calls
            stopImmediatePropagation(), so Webflow's bubbling handler never
            executes; the script then performs the fetch() POST to Netlify.
  Note    : the alternative — stripping the w-form class — was rejected
            because that class also carries the form's visual styling.

ISSUE 5 — video regression, corrected
  During the earlier video investigation the hero source had been switched
  from hydro.mp4 to sq_mp4.mp4 — substituting a different clip rather than
  fixing the actual one. Client pushed back: "work on the issue, don't change
  the issue totally." Correct call. Reverted to hydro.mp4 and preload tags
  stripped from index.html and pumps.html, then the real fix (re-encoding the
  same footage) was applied in 3.1.
  Lesson recorded: fix the asset, don't swap the asset.

B. SUPABASE BLOG + CRM — ARCHITECTURE DECISIONS
-------------------------------------------------------------------------------
Three forks were settled before any code was written:

  1. ADMIN STACK -> vanilla JS + Supabase CDN SDK
     Rejected React/Vite and Astro. The site is a Webflow export with no build
     system; introducing npm + a build command for an admin panel would have
     meant maintaining two toolchains for one static site. Admin pages deploy
     exactly like every other page.

  2. AUTH -> Supabase Auth, single user
     Originally requested as "hardcoded password in JS". Pushed back with a
     specific, functional reason rather than a general security lecture:

       The anon/publishable key must ship in client JS. A password checked in
       JavaScript gates the UI but not the database. For admin writes to work
       under that model, RLS would have to permit anonymous writes — meaning
       anyone could POST or DELETE against blog_posts directly and wipe every
       post without ever loading the admin page.

     Resolution keeps the requested UX exactly (one email, one password, no
     signup, no user management) while RLS requires an authenticated session
     for every write. Same experience, data actually protected.

  3. SCOPE -> blog fully working + CRM shell

F. IMPLEMENTATION NOTES WORTH REMEMBERING
-------------------------------------------------------------------------------
  * Content is rendered through DOMPurify before injection. Because the editor
    permits raw HTML, this prevents a bad paste from injecting script into the
    live site.

  * Read time auto-calculates from word count at 200 wpm when the field is
    left blank; the editor shows a live word count while typing.

  * Slug auto-fills from the title until the slug field is manually touched,
    then stops overwriting. Duplicate slugs are caught on save via Postgres
    error 23505 and surfaced as a readable message instead of a raw error.

  * The login ?next= parameter is validated against /^[a-z0-9._-]+\.html$/i
    before redirect — an open redirect here would let a crafted link bounce an
    admin to an external phishing page post-login.

  * Public nav/footer for the two blog pages were extracted from service.html
    at build time and had their w--current markers stripped, so the blog nav
    matches the rest of the site exactly rather than being hand-rewritten.
